# The automator owns the List Recorder's lifetime; the two programs stay separate

_Contradicts ADR-0005 (List Recording is a separate program) on one point: its consequence "There are two entry points to run, each with its own log file and its own settings. Neither starts the other." The automator now starts the List Recorder, keeps it alive, and stops it with its own run. Everything else ADR-0005 decided still stands._

Two programs means two things a person must remember to start, and a List Recorder left stopped is silent in the worst way: the automator looks healthy, the Clips folder simply stops filling with other people's Clips, and nothing says so until somebody notices a person missing. The automator is already the only time keeper (ADR-0002) and already owns a recorder child and OBS itself (ADR-0004, ADR-0006), so it is the one thing on the machine that already knows when a run begins and when it ends.

We decided the automator owns the List Recorder's lifetime while its own **List Recorder Switch** (`RECORD_LIST_ENABLED`) is on: it starts one at the top of the monitor cycle, adopts a copy already running instead of starting a second one, restarts it after a death every ten seconds forever, and on Ctrl+C asks it to stop before terminating it. With the switch off the automator takes no part at all: a copy the user started by hand runs and stops exactly as it does today.

What stays separate is why ADR-0005 survives the reversal. The helper is still a program of its own — its own process, its own `STREAMS_*` settings, its own log file — and the automator supplies only the process, never a line of the Stream List. Reading, parsing, and polling the list stay inside the helper; no Schedule and no Recording Mode reaches it; and no list trouble can slow or stop the window job.

## Considered Options

- **Keep both entry points manual** — rejected: the failure is invisible. A forgotten start costs every listed person an evening of Clips with nothing in the automator's log to show it, and the person who forgot has no reason to look.
- **Fold the list into the monitor cycle** — rejected for the reasons ADR-0005 already gave: the Recording Mode is one decision about one fixed stream, folding per-person churn in puts a network list inside the window job, and it re-opens the "who keeps the clock" question ADR-0002 settled.
- **A Windows service or a scheduled task** — rejected: a third thing to install and keep, its own copy of the idea of a run, and nothing that stops it when the user stops the automator.
- **The automator owns the lifetime; the helper stays its own program** (chosen) — one thing to start, and the helper's insides are untouched: the list reading, the Retry Limit, the disk guard, and Absence Grace all keep working exactly as they do when it is started by hand.
- **Start the helper once at launch and leave it** — rejected: a helper that dies at 10 a.m. would stay dead until the next morning's restart, which is the same silent evening the first option loses.

## Consequences

- ADR-0005's "Neither starts the other" no longer holds. Its other consequences do: two logs, two blocks of settings, one shared Clips folder, and a helper that reads no Schedule and no Recording Mode.
- **Off by default.** Nothing changes for anyone who does not ask: the switch off means the automator never looks for, adopts, starts, or stops a List Recorder, and a copy started by hand is left completely alone, including at quit.
- **The helper has two endings and both are safe.** Asked to stop, it closes every open Clip and the Clips play to their end. Killed after the ten-second wait, its Clips are still playable because of the fragment flags (commit b82eff7). If the automator itself is killed hard, its helper survives and keeps recording; the next run adopts it rather than starting a second one.
- **List Clips now sit one level down**, in a folder per Listed Person named by that person's Clean Name, so ADR-0005's argument from file names never colliding in one folder is stronger, not weaker: the names are still apart, and the folders are apart too. The automator's own timestamp-named Clips keep writing at the top of the Clips folder.
- **A recorder child now ends when the program that owns it ends**, however that program ends. On Windows a dying program does not end its children, so a killed helper could leave one recorder per person writing into the same folders while a fresh helper starts new ones. The recorder engine therefore gains one Windows job object with "kill the members when the last handle closes", created once per program run and joined by every child right after it starts. This applies to the automator's own recorder too, on purpose: today it would survive a hard-killed automator as an orphan that keeps recording, and from now on it ends with it. That is a deliberate change to existing behaviour. Where Windows refuses the job object, the engine writes one debug line and carries on with no protection — recording is never refused for it. OBS is untouched: the broadcaster launches it and it is meant to outlive the automator.
- **The automator's log gains four lines about the helper's life and nothing else**: a start, an adoption (in place of a start), a death with its restart, and a stop. The List Recorder Switch line at startup is the switch's own announcement, not one of these four. While the helper is steady the log says nothing; the helper's own chatter stays in `record_streams.log`, which the automator never writes.
- **The window job never waits on list trouble.** The start, adoption, restart, and stop all sit beside the recording update at the top of the cycle, so a helper that takes a moment to die or a list that never answers cannot slow a click, a resize, or a Recovery.
- A future reader may see two recorders sharing one engine and try to merge them, as ADR-0005 warned. Their lifetimes are now tied together, but the jobs still point in different directions — one fixed address against a changing list — and merging them would put the list back inside the window job.
